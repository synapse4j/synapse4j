# Tools

**English** | [中文](../zh-CN/tools.md)

A tool is two halves: a declaration the model sees, and the code that runs when the model calls it.
This page is both.

## The declaration

`ToolDefinition` is what reaches the model: a name, a description, and an `inputSchema` as JSON
Schema text. The schema is generated by your codec, so it describes exactly the JSON your codec
reads back. It can also carry `strict`, and provider-specific fields.

## A tool

The `Tool` interface is two methods: `definition()` and `execute(arguments, context)`. Most tools
are built from one of three classes.

**`FunctionTool`** — a typed lambda. The model's arguments decode into your type, the lambda runs,
and its result is rendered back:

```java
record Weather(String city) {}

Tool weather = FunctionTool.of(
        "get_weather",
        "Get the current weather for a city",
        Weather.class,
        (input, context) -> "Sunny in " + input.city(),
        codec);
```

The input type has to describe an object, because the protocol's arguments are an object.

**`MethodTool`** — an existing Java method. Its signature becomes the declaration: each parameter
the model provides becomes a required property of the argument schema. A `ChatContext` parameter is
filled with the conversation instead of being sent to the model:

```java
Tool weather = MethodTool.of("get_weather", "Get the weather", method, service, codec);
```

**`ManualTool`** — declaration only. Use it when you run the model's calls yourself: it carries the
declaration and refuses to execute.

## Running the calls

A bare client hands you the tool calls in the response and lets you drive them. When you want the
library to run them, wrap the client:

```java
ChatClient client = new ToolCallingChatClient(new OpenAiCompletionsChatClient(http, codec, config));
```

`ToolCallingChatClient` runs the model's tool-call rounds until the model stops asking, appending
the calls and their results to the request as it goes. The last answer is left for you to
`continueWith`.

## The execution policy

The loop runs each round's calls through a `ToolExecutor`. The default, `DefaultToolExecutor`,
resolves each call by name, runs the batch inline in order, and answers a failed call with its
message marked as an error:

```java
ToolExecutor executor = new DefaultToolExecutor();
ChatClient client = new ToolCallingChatClient(inner, executor);
```

Its constructors also take:

- an `ExecutorService` — run the batch concurrently instead of inline, still assembling the results
  in call order;
- an `ErrorHandler` — where a failed call goes: back to the model as text it can retry against, or
  out to the caller. `ErrorHandlers.message(prefix)`, `.fixed(text)` and `.rethrow()` are the
  ready-made ones;
- a `maxTurns` cap — decline a batch once the round has run that long, ending the loop where it
  stands.

A call naming no available tool fails with `ToolNotFoundException`, and travels the same path as
any other failure.

## Registering tools on the client

A tool can sit on the request, or stand on the client and be merged into every request:

```java
client.addDefaultTool(weather);
```

A `ToolProvider` is the dynamic counterpart: it is asked on every call, so the tool set can change
behind the client:

```java
client.addToolProvider((c, request) -> List.of(weather));
```

## Letting the model choose

`ChatOptions.toolChoice` says whether the model may call a tool — `auto`, `none`, `required`, or
`tool` for one named tool:

```java
ChatOptions options = new ChatOptions();
options.setToolChoice(ChatOptions.TOOL_CHOICE_REQUIRED);
```
