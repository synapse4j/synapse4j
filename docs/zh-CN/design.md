# 设计与取舍

[English](../en/design.md) | **中文**

本文说明 synapse4j 做什么、刻意略过什么，以及为什么。如果你在动手用它之前想确认这个库合不合适，
或者正准备改动它，都值得一读。

## 它建模并传输一次调用，但不记住这次调用

库负责构建请求、发送请求、把答案读回来。这就是它的全部工作。

它不跨调用保存任何东西。对话历史、你把它存在哪里、如何裁剪、以及把一段对话从一个提供商迁到另一个
提供商时会发生什么，全都是你应用的决策。库只把数据交给你，别的不管。

这是它与框架最主要的区别。框架替你掌管对话，也就同时掌管了对话如何存储、如何压缩、如何迁移——而这些
决定你可能想自己做。也正是这一点让库得以保持无状态：一个客户端就能服务应用里的所有请求，不必为每段
对话各建一个实例；每次调用都显式接收全部输入。

一段对话靠你提供的标识符串起来。库只是把它透传，从不存储。

## 所有提供商共用一套模型

一次调用的大部分内容是各家都认同的：带角色的消息、模型名、温度、工具列表。共享的请求与响应类型表达的
就是这块共识。

难点在其余部分，因为各家并不认同。库用四种方式处理：

1. **它没有建模的字段会被保留，并原样发回。** 每个能携带这类字段的节点——消息、内容部分、工具——以及
   调用自身的选项，都能在库认识的字段之外再携带提供商特有的字段。提供商发来、而库叫不出名字的东西，会
   留在它来自的那个节点上，节点再次发出时原样写回，所以一次往返下来不会丢东西。

2. **只有当某个字段必须跨提供商保留下来、且各家对它的含义有共识时，它才进入共享模型。** 两家提供商有
   一个名字相似的字段并不够。这个字段必须确实需要跨提供商，*并且*各家的取值能映射到同一个含义。

3. **共享字段若某个协议无法表达，就不发出去，调用照常进行。** 提供商没有对应的成员，你设置的值它就不
   发；若因此拒绝调用，一换提供商同一段代码立刻就会坏，而这正是这个库要防止的。唯一的例外是对答案形状
   的要求：协议兑现不了时调用失败，因为一个违反要求却看起来像成功的答案，是代价最高的一种错误。

4. **提供商对共享字段的拼写，是该模块上的配置。** 各家端点对名字有分歧——一家要
   `max_completion_tokens`，另一家要 `max_tokens`；一家把推理内容放在 `reasoning` 下，另一家放在
   `reasoning_content` 下。那个名字是模块配置上的一个选项，读和写共用，默认值适合该提供商。它从不根据
   某次响应恰好含有什么来猜测，因为一段读了某个拼写却写另一个拼写的对话，会把端点从未发出过的成员
   改名。

原样透传的东西就原样透传：模块一字不差地写回它读到的。把对话在提供商之间迁移，是你应用刻意做的一件事，库不会去
猜。

## JSON 库和 HTTP 客户端由你选

库自己不序列化任何值，也不自己开连接。它让一个 JSON 编解码器把值变成 JSON，让一个 HTTP 客户端发送
字节。两者在 core 里都是接口，实现放在各自的模块里。

与之相对的做法——直接依赖 Jackson 和 JDK 客户端——会让这些选择永久固定下来。在这里，你可以换掉其中
任何一个，提供商模块和你的代码都不用改。模块的拆分就源于这条规则：core 只给出接口，每个 JSON 或
HTTP 库各有一个自己的模块。

## 生成的 schema 承诺了什么

schema 从 Java 类型生成，只作一个承诺：schema 允许的，编解码器一定收下。它可以承诺得更少——发给模型的那份
就有意如此——但绝不会更多。

这个承诺是有方向的。你交给 JSON 产出方的 schema——模型要调用的工具的入参、结构化答案的形状——是
decode schema：编解码器愿意读什么。描述本库产出物的 schema——告诉模型一次调用会返回什么——
则是 encode schema。两者可以不同；绑定器不对称的地方，两者就会不同。

decode schema 跟着类型走，而不是跟着绑定器的宽容度走。类型声明为可空的值——`Optional`、`OptionalInt`
这一类——既可以缺席也可以是 null，无论写在哪里：方法参数、属性、列表元素、Map 的值。其余的都必填且不可空。
`Map` 保留自由键，值类型就成为 `additionalProperties`。声明了属性的对象，是否封闭取决于读的一方：
读的一方拒绝未声明属性时封闭——写 `additionalProperties: false`——接受时则保持开放。
比绑定器更严的是必填与可空这部分：绑定器会把缺席的 `String` 当成 null 收下，
而这份 schema 干脆不把这个余地留给产出方。

encode schema 反过来跟着 mapper 走，因为它描述的是写出去的真实结果。mapper 每个属性都写时，
每个属性都必填；一旦 inclusion 设置可能省略某个值，它就不再必填。

至于某个提供商收不收这份 schema，是另一回事。有的要求所有属性都进 `required`，有的用自己的写法表达可空，
有的只认关键字的一个子集——这些转换属于提供商模块，不属于 schema 生成器。
一个编解码器服务你对接的所有提供商。

## API 长什么样，以及为什么

**阻塞，而非响应式。** 调用在答案完整后返回。异步交给 JDK——Java 21 虚拟线程——而不把库绑到
Reactor 或 RxJava 上。这样线程模型保持简单，也是库里没有任何东西把事件推给你的原因。

**流式与非流式共用同一个请求。** 请求只写一次，如何消费答案由你选。流式调用把提供商的事件按到达
顺序交给你，并组装回阻塞调用会返回的那个轮次。

**结构开放。** 用户或提供商会扩展的类型，不是 `enum`、`record` 或 `final` 类。`enum` 无法增加
取值，`record` 无法携带额外字段；两者都会阻断这套模型本要允许的扩展。已知会增长的取值——角色、结束
原因——是字符串加具名常量。只有规范固定了集合、没有东西会扩展它时，才使用封闭形式。

**先有需要，再做抽象。** 一个新抽象要长出来，至少得有两个真实实现，不能靠对第三个的猜测。

**默认更省。** 在别的原则把选择权留出来的地方，库选更省的做法——内存更少，中间步骤更少：请求边写边发，
而不是先构建成一棵树再整体序列化；响应也以同样的方式读取。

## 非目标

- 不做 agent 编排或工作流引擎。
- 不做对话记忆。历史是你的。
- 不绑定某个具体的 JSON 库、HTTP 客户端或 LLM 提供商。
